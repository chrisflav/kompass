A section’s finance rules

A section’s finance rules¶

Kompass does not know how your section settles an excursion. It knows how to read a statement out of the database, how to run your rules against it, how to make the money add up and how to remember which version of the rules a statement was settled under. The rules themselves — what an allowance is, who gets it, what the participants contribute, who has to sign — are a Python package in your section’s own configuration repository.

This page is the reference for writing that package. It is the whole contract: kompass.rules is the only Kompass module a ruleset may import, and everything it offers is documented below.

Tipp

There is a directory in this repository to copy rather than start from nothing: deploy/config-template/. It holds a working ruleset, three worked cases, the mypy and ruff configuration and a CI workflow. Its README.md is the section’s half of this page.

What a ruleset is¶

A ruleset is a class deriving from Ruleset, instantiated once and exported as ruleset:

# rules/__init__.py
from kompass.rules import PARTICIPANTS, Ruleset, SECTION

class TownRules(Ruleset):
    name = "town"
    context_version = 1
    balance = (PARTICIPANTS, SECTION, "participant_contribution")

    ...

ruleset = TownRules()

It answers four questions about one statement, and nothing else:

inputs()

Which extra data does a person have to supply? The form is derived from these declarations, so a question is asked because a rule reads its answer.

transfers()

Who owes whom how much, and what is wrong with the statement?

checks()

What must hold before the statement may be handed in?

approval()

Who has to sign it off, and who may not?

Each one is given a RuleContext — every fact about the statement a rule is allowed to know, as frozen values.

There is a fifth method, and it matters to anyone whose questions depend on the answers already given: the live form asks relevant_inputs(), not inputs(). Its default implementation re-runs inputs against the answers so far, which is why a ruleset that branches inside inputs already works.

The two have different jobs, and it is worth saying which is authoritative for what, because a ruleset that overrides relevant_inputs is overriding only one of them:

inputs says what may be read. It is the whole vocabulary: every key a rule may ask for, every key an answer may be stored under, and the list the case runner, the fuzzer and the deleted-member cleanup all go through. A rule that reads a key inputs never declared raises RuleError.

relevant_inputs says what is being asked. It is the form, and it is the set an answer has to be in to count. A question it leaves out is off the form, clean refuses an answer for it, and — since this was settled (taxis #579) — the rules read it as unanswered: the type’s empty value, exactly as if nobody had filled it in yet, whatever is still stored under the key.

So what the form does not ask, the rules read as unanswered. Retiring a question therefore stops it moving money, which is the point: before, the stored answer went on reaching the rules from behind a form that no longer showed it and a clean that no longer accepted it, and the only way out was an admin editing JSON. Reading a retired key is not an error — it reads empty — because a traceback about a question nobody can see is worse than a zero a rule can handle.

Narrow, do not widen. relevant_inputs chooses among the questions inputs declared, and two things follow that are worth stating plainly:

  • A key only relevant_inputs names has nowhere to be stored and nowhere to be read, so it is an error on the statement — not a question that quietly never gets an answer.

  • A key they both name is served with the declaration inputs gave it: same label, same type, same bound, same source. So a ruleset that overrides one method and not the other cannot end up with a form that says an answer is the person’s to give while the engine supplies one anyway.

How a ruleset reaches a running instance¶

Every Kompass instance is the stock image with one directory mounted read-only at /app/config (KOMPASS_CONFIG_DIR_PATH), the same directory settings.toml is read from. A ruleset is a package in that directory, named from the settings:

[finance]
ruleset = "rules"   # a package directory under KOMPASS_CONFIG_DIR_PATH

manage.py importruleset runs when the master container starts — one of the five the image runs, and the only one whose entrypoint imports; the SPA, the Celery worker, the beat and the LMTP containers do not — on demand from the admin, and, with [finance] ruleset_poll_minutes, from a periodic task. It reads every *.py under the package, hashes the sources together with the section’s finance parameters, and stores that as a version. An unchanged package hashes to the version that is already stored, so importing twice costs a hash and changes nothing.

A section’s workflow is therefore: pull request in the configuration repository → its own CI runs mypy, ruff and checkruleset inside the pinned image → merge → the host pulls the repository → import. No Kompass release and no container restart: workers resolve the active version per evaluation and load its sources by hash on first use.

Activation is gated on the same checks the section’s CI runs. A package that fails one of them is stored as a draft, the previous version stays active, the command exits non-zero and says so loudly — and the container still serves. A typo in a rule is not a reason to take a section’s finances offline.

A statement keeps the version it was created under: its own copy of the sources and of the parameters is snapshotted onto it, and the resolved transfers are written down as rows. Changing a rule — or a parameter, which is the same thing to the hash — never moves a figure that has already been settled.

Warnung

A section that deploys without a ruleset settles its statements under Heidelberg’s rules. When [finance] ruleset is unset, the reference ruleset that ships in the image applies, and that ruleset is the policy of the JDAV section Heidelberg: its allowance per day, its organisation fee for participants from 27, its LJP arithmetic, its single signature from the finance department.

Nothing fails and nothing warns: the statements resolve, the books add up, and the figures are somebody else’s. For any section that is not Heidelberg, writing a ruleset is not optional — it is the difference between settling your own rules and settling theirs.

The rules of the road¶

Six properties the engine enforces or depends on. Each of them is the reason an old statement can be re-derived years later and come out the same.

Everything is a frozen value¶

The context holds no model instances, no relations to follow, no names, no bank details, no other statements and no balances. A person is a Member — an id and nothing else — and the engine resolves names and bank details after evaluation, so a ruleset cannot leak them. What a rule cannot reach it cannot accidentally depend on.

A rule must not query the database¶

This is enforced, not asked for: while any of the four methods runs — and while the ruleset’s own module body is executed, and while the engine reads name, context_version, valid_from or permissions off it — every ordinary route to the database refuses. A query raises QueryDuringEvaluation, which comes back as an error on the statement with the traceback pointing at the line in your rules.

Everything a rule may read is in the context it was given. If a rule needs a figure that is not there, the answer is a new context field in Kompass — an additive change with a CONTEXT_VERSION bump — and not a query.

Money is Decimal, in whole cents¶

Never float. Every amount a rule returns must have at most two decimal places; the engine rejects anything finer rather than rounding it silently, because how to round is the section’s decision and not the engine’s. split() and pct() are the two roundings most rules need, and quantize() is the one they are built on. A transfer whose amount is a float, or has three decimal places, is an error on the statement rather than a payout nobody can reproduce.

Rules are deterministic¶

There is no clock in the context and no way to read one: a call to now, today, utcnow or fromtimestamp is refused by the import check, and random and time may not be imported at all. The one value that depends on when the engine ran is age, which exists because the rules it was ported from use it; a rule that must stay reproducible prefers age_at_start.

A rule must also not read balances — neither a member’s standing with the section nor what another statement resolved to. The context deliberately has none. The only result of another rule a rule may read is the transfer list it has built itself during this evaluation, which is how the reference ruleset’s LJP contribution reads the allowance and subsidy it just produced.

balance names the residual party, and it may not be a member¶

A ruleset does not compute the participants‘ contributions. It declares which two parties the residue moves between (balance), and the engine appends exactly one transfer with the amount that brings the declared destination to zero. „The statement adds up“ is therefore not an assertion anybody can forget to make.

The declaration must be between the section and the participants. A member may not be a balance party: a person is a payee, not a ledger, and balancing against one makes whoever it names the sink for everything the rules did not account for — a bill nobody wrote. The engine refuses it. It also refuses a declaration that is the wrong way round, which closes nothing and leaves a 0.00 row to show for it.

A ruleset is stateless¶

One instance is created when a version is loaded and that instance is shared across every evaluation in the process, concurrently, for as long as the version is in use. Do not keep anything on self between calls: no caches, no counters, no „the statement I am working on“. Everything a method needs is in the context it is given, and anything stored on the instance is a figure from somebody else’s statement waiting to be used in yours.

What does not change is fine: a number read from the context (ctx.params.ALLOWANCE_PER_DAY), a module-level constant (ORG_FEE_AGE = 27), a class attribute the engine itself reads (balance), a pure helper method.

What a ruleset may import¶

A ruleset may import:

  • itself — relative imports inside its own package (from .travel import reimbursement),

  • kompass.rules, and nothing else from Kompass,

  • from __future__ import …, which is a compiler directive,

  • and these standard-library modules: decimal, math, dataclasses, typing, enum, fractions, itertools, functools, collections.

Everything else is refused at import time, with a file and a line. So is any mention of __import__, importlib, exec, eval, compile, open, os, sys, subprocess, socket, random, time, requests, anything under django, globals, locals, vars, getattr, setattr, delattr and dir; so are the dunder attributes that walk out of a module and into the interpreter (__class__, __globals__, __builtins__, __code__ and the rest); and so is a call to now, today, utcnow or fromtimestamp.

Third-party packages are not available. The image does not have them, and a ruleset’s import closure has to be enumerable to be hashable. A section that needs more than the list above asks for a helper in kompass.rules.

Wichtig

This is a lint plus a restricted namespace. It is not a sandbox, and nothing here should be read as one.

The check is a textual scan of the ruleset’s source, and the loader executes it with a restricted __builtins__. Neither is a boundary: four lines that mention no banned name at all reach the interpreter’s own builtins through a frame object, and frames, descriptors and __reduce__ are each one hop from the next spelling. No blacklist carries that guarantee.

What the check is worth is catching the accident early — a rule that imports half of Kompass, reads the clock or opens a file is a rule whose answer can change behind an old statement’s back — and letting your own CI say the same thing with ruff before the pull request is merged. What carries the database guarantee is the query guard, which refuses at the connection however the rule got there.

The trust boundary is unchanged by any of it: whoever can write the configuration directory already holds the database password and the secret key. Executing Python from it grants no privilege its author does not already have. A rule author is trusted exactly as far as the person who edits settings.toml.

Declaring inputs¶

Every answer a rule reads has to be declared by inputs(), because the statement’s form is generated from those declarations. Reading an undeclared key raises RuleError rather than returning None: a typo in a rule is a bug your cases should catch, not a silent zero in somebody’s reimbursement.

The widget vocabulary¶

type is presentation, not rule structure — money and int are both numbers, and the difference is the field the person is shown.

type

Read with

What it is, and what it reads as unanswered

money

money()

An amount, as a Decimal. Unanswered: 0.00.

int

number()

A whole number; max is its largest acceptable value. Unanswered: 0.

bool

flag()

A yes/no question. Unanswered: False.

text

text()

Free text. Unanswered: "".

choice

text()

One of the named alternatives in choices, as its value. Unanswered: "".

member

member()

One person out of options. Unanswered: None.

member_set

members()

Several people out of options, at most max of them. Unanswered: ().

For member and member_set, the engine re-validates a submitted answer against the options the declaration offered, so an answer can never name somebody the rule did not offer. A choice is re-validated against its own choices in exactly the same way, so an answer can never be a value the rule did not offer either.

And it is re-validated on the way out, not only on the way in. A domain shrinks without anybody editing an answer: a section withdraws one of two alternatives, or a receipt’s payer is cleared and an options_source set loses them. The answer stored under that key then reads as unanswered — the same reading a retired question gets, and for the same reason: what the form would refuse, the rules do not read. GET …/form serves it as unanswered too, so a client is never handed a value its own option list does not contain.

So one sentence holds for the whole form: what the form serves is what the rules read, and the only answer a client may not send back is a derived one.

Any key can be stored. A statement keeps its answers in one JSON field, so a declaration under any key a ruleset likes holds an answer and is read back by the rules. That is a statement about storage, and it is the whole of what #556 changed.

Warnung

Four key names still mean something outside the engine, and a section that renames them loses what they do silently. finance/models.py reads allowance_to and night_cost by name, out of Statement.inputs, in properties the engine never sees:

  • allowance_to_valid → validity → the admin’s confirm() and submit_statement. It is the INVALID_ALLOWANCE_TO gate, and with the key absent it returns True vacuously — so a section whose allowance key is called something else keeps the gate’s name on its screens and none of its checking.

  • real_night_cost → the statement summary’s price_per_night, which is what the printed PDF shows.

Those are leftovers of the four columns rather than anything the rules engine asks for, and until they are derived from the declarations too, a section reusing the names keeps the behaviour and a section renaming them should know it is giving the behaviour up.

A declaration the engine cannot serve is refused where it is written, with RuleError — a choice with no choices, a source naming a field the context does not have, an options_source on a question that names no people. Inside inputs that becomes an error on the statement with a traceback at the line in your rules, and in your own CI it fails a case before the version is ever activated. The alternative, which is what choice used to do, is a question that reaches somebody’s form with nothing behind it.

A choice names its own alternatives¶

A choice has to say what may be chosen, as Choice values. The value is what is stored and what a rule reads; the label is what the person picking it is shown, so a section can reword the question without touching the rules or re-settling anything:

Input(
    "regime",
    "Nach welchem Regelwerk?",
    "choice",
    choices=(
        Choice("ehrenamt", "Ehrenamtspauschale"),
        Choice("tourenleitung", "Tourenleitung"),
    ),
)

# and in `transfers`
rate = RATES[ctx.inputs.text("regime")] if ctx.inputs.text("regime") else ZERO

An unanswered choice reads as "", like an unanswered text — so a rule reading one on a form somebody is halfway through gets an empty string, not an exception.

Derived inputs: a figure the statement already knows¶

Some of what a rule needs is not a question at all. The kilometres are on the excursion; asking a person to type them again invites two numbers that disagree. A declaration may therefore name where its value comes from:

Input("kilometers", "Gefahrene Kilometer", "int", required=False,
      source="excursion.kilometers")

With an excursion whose source resolves, the engine supplies the value. The declaration comes back with derived set, the form shows the figure rather than an empty field, and submitting a value for the key is refused — a 422 keyed by that question. Wrong kilometres are corrected on the trip.

Without an excursion, or with nothing recorded, it is an ordinary question whose answer is stored like any other.

Either way the rule reads it the same way:

kilometers = ctx.inputs.number("kilometers")

That is the whole point. Before, the same quantity lived in two places depending on provenance — ctx.excursion.kilometers off the trip, everything else out of inputs — so a ruleset serving statements both with and without an excursion had to branch on ctx.excursion is None and read a different place in each arm. One declaration and one accessor replace that.

A derived value is not stored. It is resolved again every time a context is built, never written to Statement.inputs. That is a decision rather than an omission: a stored copy would be a second figure to go stale when the trip is corrected, there would then be a question about which of the two is right, and re-seeding it would need a rule nobody has written. There is no second copy — the excursion is the record.

A source is "<root>.<field>", one field deep. The roots are SOURCE_ROOTS: excursion and statement. The field has to be a real field of what that root holds — a field of Excursion or of StatementInfo — and anything else is refused where it is written, with the list of fields that do exist. There is no deeper path, no callable from the ruleset and no getattr chain over arbitrary objects: the engine looks up one named field of one frozen dataclass it built itself, which is what keeps the query guard’s story intact. A figure further in than one field — ctx.excursion.ljp.participant_count — is read off the context by the rule that wants it, which needs no declaration at all.

The value arrives as the type the field holds: excursion.kilometers is a whole number, excursion.duration is money, statement.creator is a Member, excursion.leaders is a set of them. Match the widget to the field; naming a field that holds a whole nested structure is a mistake the form will show you as text.

A source resolves to nothing in exactly two cases: the root is absent (a statement with no excursion) or the field itself is None. A 0, an empty string and an empty set are figures the statement records, so they are supplied like any other — a trip whose kilometres are still at the model’s default of 0 serves 0 and refuses a correction on the form, because the correction belongs on the trip. The only nullable fields are StatementInfo’s two people and ljp.

max applies to a derived value too, and that is worth knowing before writing source="excursion.leaders" with a bound on it. A submitted answer over the bound is refused on the way in; a supplied one cannot be, because nobody can change it here — so it is an error on the statement naming the source and the bound. Five leaders against three the section approved is a statement to fix on the excursion, and while the error stands the statement does not resolve and no money moves. It is deliberately not a truncation: paying three of five quietly is a figure no page explains.

A source may not be stated beside options or options_source, and that is refused where it is written. A derived answer is not picked, so „these are the people who may be picked“ and „the value is whoever the trip says“ are two answers to one question. A derived set of people is bounded by max, and is already statement-local because the context is.

Where a party-valued question’s people come from¶

member and member_set need a domain, and a ruleset that has an excursion can simply write one: options=ctx.excursion.leaders. A statement that settles a purchase rather than a trip has no leaders — and so, until this, no way to pay anybody at all.

A declaration may instead name where the engine should take them from:

Input("paid_to", "Auslagen an", "member", required=False,
      options_source="bills.payers")

The vocabulary is OPTION_SOURCES, and it is a fixed list rather than a path on purpose: this is the one declaration where a mistake costs money, so every name in it is a set the statement itself carries.

excursion.leaders

the trip’s youth leaders — what a trip-shaped ruleset writes by hand.

excursion.participants

everybody on the trip’s member list, leaders included.

bills.payers

whoever paid one of this statement’s receipts. The answer for a purchase.

statement.creator, statement.submitter

the two people the statement names itself.

No spelling of it reaches somebody the statement does not already mention, and „every member in the section“ is not reachable. The engine fills options in, deduplicated and in id order, and the submitted answer is then re-validated against it like any other. Say it once: a declaration that both lists its options and names a source for them is refused.

Steps: which questions belong together¶

The declarations are a flat list, so a client can only lay them out as one long form. step is a short label that says otherwise:

Input("regime", "Regelwerk", "choice", step="Grundlagen", choices=...)
Input("kilometers", "Kilometer", "int", step="Fahrt", source=...)
Input("paid_to", "Auslagen an", "member", step="Fahrt", options_source=...)

GET …/form then serves steps as well as inputs: a label and the keys in it, in declaration order, with the steps in the order their labels first appear. Every key is in exactly one step, and a ruleset that names none comes back as a single step with an empty label — so a client can render the grouping unconditionally.

That is all it is. There is no page state, no „next“, no notion of a step being complete: which questions belong together is the section’s business, how to present them is the client’s, and a wizard in the backend would be Kompass deciding both.

The section’s numbers¶

A figure that the section votes on rather than a rule that it writes — the allowance per day, the maximum per night, the rate per kilometre — is a parameter, read from the context as ctx.params.ALLOWANCE_PER_DAY. The values come from the section’s settings.toml, as exact decimal strings, and they are hashed into the ruleset’s version alongside its sources: changing the allowance per day is a new version, not an edit, and nothing that was settled under the old number moves.

Bemerkung

The parameter names are not free-form. Kompass copies a fixed list of settings into a version’s parameters — PARAMETER_KEYS in finance/engine/context.py, today ALLOWANCE_PER_DAY, MAX_NIGHT_COST, AID_PER_KM_TRAIN, AID_PER_KM_CAR and EXCURSION_ORG_FEE (from [finance]) plus LJP_CONTRIBUTION_PER_DAY and LJP_TAX (from [LJP]) — so ctx.params.WHATEVER_YOU_LIKE raises RuleError.

A number that is not one of those keys belongs in the ruleset as a module-level constant, where it is versioned with the rules that read it. That is arguably where a figure the section voted on belongs anyway: the hash moves when it changes, which is exactly the behaviour a parameter has.

Cases: a ruleset’s own tests¶

A case is one JSON file beside the rules, in rules/cases/*.json, holding a whole context and what the rules are expected to make of it. It needs no database, no fixtures and no Django, which is the point: the cases run in your own repository’s CI against the image you deploy, and the instance runs them again at import — a case that fails means the version is stored as a draft and never activated.

{
  "name": "allowance only",
  "params": {"ALLOWANCE_PER_DAY": "22"},
  "inputs": {"allowance_to": [7]},
  "excursion": {"duration": "2.0", "leaders": [7], "staff_count": 1,
                "approved_staff_count": 2},
  "expect": {
    "transfers": [
      ["SECTION", "7", "44.00", "allowance"],
      ["PARTICIPANTS", "SECTION", "44.00", "participant_contribution"]
    ],
    "errors": [],
    "checks": [true]
  }
}

  • Only the keys a case cares about have to be there. Everything else takes a quiet default: no bills, no trip, no answers, every parameter unset.

  • Money is written as a string ("42.69"), so that a case file never carries a binary float.

  • A party is "SECTION", "PARTICIPANTS" or a member id.

  • Each expected transfer is [source, destination, amount, category], in the order the rules produced them, and the engine’s balancing transfer is the last one. A case that leaves it out fails, which is deliberate: it makes the case say out loud what the participants end up contributing.

  • errors is the list of messages transfers() returned, compared exactly.

  • checks is the expected ok state of each check, in order. Leaving the key out means the case does not look at them.

  • permissions maps a codename to the ids that hold it, for a ruleset whose rules read permission_holders().

The format is implemented in jdav_web/finance/engine/cases.py, which is also where a new key would be added.

What a case cannot prove about a derived input¶

A case answers questions, and a derived question is not answered: the engine resolves it from the context the case file describes. So writing kilometers into a case’s inputs proves nothing — the engine will supply excursion.kilometers over it, exactly as it does on a real statement. Put the figure where the rule will read it from:

{
  "name": "travel at the volunteer rate",
  "inputs": {"regime": "ehrenamt", "paid_to": 7},
  "excursion": {"kilometers": 100, "leaders": [7]},
  "bills": [{"amount": "40.00", "payer": 7}],
  "expect": {"transfers": [["SECTION", "7", "20.00", "travel"],
                           ["PARTICIPANTS", "SECTION", "20.00",
                            "participant_contribution"]]}
}

A case can prove the other half, and it is the half worth a case: leave excursion out and the same declaration is an ordinary question, so a case with "inputs": {"kilometers": 250} and no trip is the statement that settles a purchase. Both arms of one declaration, in two files.

An option source is resolved for a case too, out of the context the file describes: the bills above are where options_source="bills.payers" finds member 7. A case’s own answers are not validated against it — the case runner types them and nothing more, the same as it has always done — but --fuzz answers a party-valued question out of exactly that set, so a ruleset whose option source comes out empty is a ruleset the fuzzer will keep offering nobody to.

Checking a ruleset¶

checkruleset runs the import check, loads the package, and runs its cases. It touches no data, so it runs anywhere the image runs:

docker run --rm -v "$PWD":/app/config:ro \
    -e KOMPASS_CONFIG_DIR_PATH=/app/config \
    ghcr.io/chrisflav/kompass:<tag> \
    python jdav_web/manage.py checkruleset /app/config/rules --fuzz 200

KOMPASS_CONFIG_DIR_PATH makes the fuzz use the numbers from the settings.toml beside the rules; the cases carry their own params. The command keeps the image’s own working directory, /app, which is where it has to run — see the warning below.

--fuzz N additionally builds N random but valid statements, asks the ruleset what to ask the person, answers those questions at random within the domains the ruleset itself declared, and checks the two things that must hold whatever the answers are: that the rules report no error, and that the books balance. It is not a proof and it is not a substitute for a case with an expected figure — it is the cheapest way to find the rule that divides by a participant count nobody checked for zero.

A section’s CI runs three commands, all three inside the image the instance runs, so that the API module and the interpreter match production. They do not share a working directory:

cd /app/config && mypy --strict rules      # reads ./pyproject.toml
cd /app/config && ruff check rules          # reads ./pyproject.toml
cd /app && python jdav_web/manage.py checkruleset /app/config/rules --fuzz 200

Warnung

The third command must not run from /app/config. Kompass pulls in Celery, whose Django fixup inserts the working directory at the front of sys.path on purpose, and a configuration directory contains a rules/ package — which is also the top-level name of django-rules, a dependency and an installed app. From /app/config the section’s own ruleset shadows it and django.setup() dies with No module named 'rules.contrib' before a single rule is read.

So checkruleset runs from /app, exactly as the container entrypoint does, and is given the package by absolute path. mypy and ruff do need /app/config as their working directory, because that is where their pyproject.toml is; neither imports Django, so neither is affected.

The exact invocation — the mount, the environment and where mypy and ruff come from, since the image carries the application’s dependencies and not a toolchain — is .github/workflows/check-rules.yml in deploy/config-template/.

mypy --strict is worth having because the accessors are typed: a Decimal + bool, a destination that is an int rather than a Member, a rule that forgot excursion may be None — all of those are a file and a line rather than an error on somebody’s statement. ruff, with the banned-import rules the template ships, reports a forbidden import as a lint failure in your own CI instead of a rejected version in the admin.

A section without CI has checkruleset by hand and the admin’s dry run. That is less, and it is stated as less.

API reference¶

The ruleset¶

class kompass.rules.Ruleset¶

What a section’s finance rules have to implement.

Subclass it in the section’s ruleset package and export one instance as ruleset:

ruleset = HeidelbergRules()

Everything the engine fixes is here; everything else — how many rules there are, what the categories mean, who a recipient is, whether an amount is per person or per statement — is the author’s Python.

name: str = 'unnamed'¶

A short name for this ruleset, used in logs and in the admin.

context_version: int = 1¶

The CONTEXT_VERSION this ruleset was written against. Kompass refuses to load a ruleset written against a newer context.

valid_from: str = ''¶

The date these rules were in force from, ISO 8601 ("2026-03-01"), empty for „from the moment Kompass is told“.

It is valid time, and it may be in the past: a section that resolved new rates in March and imports them in May says "2026-03-01", and the record then carries both when the rules applied and when Kompass learned of them. A date in the future stages a change that is already agreed. This declaration is the authority for either, which is why it lives in the ruleset package rather than in a command-line flag: the package is reviewed and committed, and it is the versioned documentation of the procedure an auditor asks for.

Backdating records; it does not re-settle. A statement is bound to the rules it was created under, and no version imported afterwards — with whatever date — changes what it settled under; settling one again under a correction is a separate, deliberate act (#561).

permissions: tuple[str, ...] = ()¶

Permission codenames the rules read with RuleContext.permission_holders(). The engine resolves these before evaluation, because the rules cannot query the database themselves.

balance: tuple[Member | Section | Participants, Member | Section | Participants, str] = (Participants(), Section(), 'balance')¶

(source, destination, category) of the one transfer the engine appends, with the amount it resolves itself: the amount that brings destination’s net position to zero. Declaring the parties and letting the engine do the arithmetic is what makes „the statement adds up“ unfalsifiable rather than asserted. When the resolved amount comes out negative the engine runs the transfer the other way round, so the direction declared here is the one that is usual for the section.

abstractmethod inputs(ctx: RuleContext) → list[Input]¶

Declare every answer the rules read, in the order to ask for them.

abstractmethod transfers(ctx: RuleContext) → tuple[list[Transfer], list[str]]¶

Resolve the statement into transfers, plus anything wrong with it.

Return (transfers, errors). An error is a sentence for the person who has to fix the statement — a covered bill with nobody to pay back — and while there is one, nothing is persisted and no money moves. Do not raise for a problem with the statement; raising is for a broken ruleset, and the engine turns it into an error with a traceback.

checks(ctx: RuleContext) → list[Check]¶

Preconditions for handing the statement in. Default: none.

relevant_inputs(ctx: RuleContext) → list[Input]¶

The questions still worth asking, given the answers so far.

The default re-runs inputs() against the answers known so far, which is enough for a ruleset whose inputs branches on them — drop the question about the price per night once „no subsidy“ has been answered, and it stops being asked.

This and inputs() have different jobs, and overriding this one overrides only the second of them. inputs says what may be read: the whole vocabulary, every key an answer may be stored under, and the list that reading a key is checked against. This says what is being asked: the form, and the set an answer has to be in to count. A question this leaves out is off the form, the API refuses an answer for it, and the rules read it as unanswered — the type’s empty value, whatever is still stored under the key.

So what the form does not ask, the rules read as unanswered, and retiring a question stops it moving money. Reading a retired key is not an error; it reads empty, because a question nobody can see is not something a rule should fail on.

Narrow, do not widen. A key only this names is not in the vocabulary, so it has nowhere to be stored and nowhere to be read: the engine reports it as an error on the statement rather than serving a question whose answer would silently never arrive. And a key this names is served with the declaration inputs gave it — same label, same type, same bound, same Input.source — so the two methods cannot disagree about one key.

approval(ctx: RuleContext, transfers: list[Transfer]) → tuple[list[Constraint], list[Forbid]]¶

Who has to sign this statement off, and who may not.

Routing runs on the transfers, after expansion, so a rule can say „nobody who receives money from this statement“ (see Forbid) or „over 1.000 € it takes the board“ without re-deriving either from the raw statement. Default: nobody, which the engine reads as „the capability check alone decides“.

kompass.rules.CONTEXT_VERSION: int = 1¶

The version of the context shape this Kompass offers. A ruleset declares the version it was written against in Ruleset.context_version, and Kompass refuses to load one written for a newer context. Changes are additive — a field is added, never renamed or removed — so a ruleset written against version 1 keeps working.

exception kompass.rules.RuleError¶

Raised when a ruleset asks the engine for something it may not have.

Rule authors do not raise this. Problems with a statement are reported by returning a message from Ruleset.transfers(); this exception is for problems with the ruleset — an input it never declared, a permission it never asked for — which are programming errors and should fail a case in the section’s own CI.

class kompass.rules.Inputs¶

The answers to Ruleset.inputs(), by key.

Reading a key the ruleset did not declare raises RuleError rather than returning None: a typo in a rule is a bug the section’s own cases should catch, not a silent zero in somebody’s reimbursement. A key that was declared but never answered reads as that type’s empty value — 0.00 for money, None for a member, () for a member set.

The accessors are typed, so mypy checks the arithmetic a rule does with an answer:

nights = ctx.excursion.nights * ctx.inputs.money("night_cost")

ctx.inputs.night_cost reads the same answer untyped, for a quick look. A key that happens to be named like one of the accessors — money, member, members, number, flag, text, raw, declared — is readable through those and through raw(), but not as an attribute, where the method wins.

Prefer money(), member(), members(), number(), flag() or text(), which say what they expect.

A money answer, as a Decimal.

number(key: str) → int¶

A whole-number answer.

flag(key: str) → bool¶

A yes/no answer.

text(key: str) → str¶

A free-text answer.

member(key: str) → Member | None¶

A single person, or None when nobody was picked.

members(key: str) → tuple[Member, ...]¶

A set of people, possibly empty, in the order they were picked.

class kompass.rules.Roles¶

Who holds which section role — or a refusal to guess.

A mapping, so ctx.roles["kassenwart"] reads as one, with one difference that matters: a context built for the arithmetic does not resolve the role assignments, and reading them from there raises RuleError instead of answering ().

That asymmetry is deliberate. An empty mapping cannot distinguish „nobody holds this role“ from „nobody asked the database“, and the second one, silently, pays a treasurer nothing and balances the books around the hole. Roles are resolved for Ruleset.approval(), which is what they are for; a rule that routes money by a role has to say so, and until the engine offers that it says so by failing loudly.

get(role, default=())¶

The holders of role, or default when nobody holds it.

Documented here rather than inherited: the signature comes from Mapping, but the behaviour does not. The default is () rather than None, and on a context that did not resolve the role assignments this raises RuleError instead of returning the default — which is the whole point of the unresolved state, and the opposite of what Mapping.get’s own docstring says.

class kompass.rules.Transfer(source: Member | Section | Participants, destination: Member | Section | Participants, amount: Decimal, category: str, rule_id: str, label: str = '', explanation: str = '')¶

Money owed by one party to another, because of one rule.

A transfer is the whole output of a ruleset. Expressing a payout as a movement between two parties rather than as a number on a member makes the books add up by construction: there is no such thing as money that appears from nowhere, and the engine’s balancing transfer (see Ruleset.balance) closes whatever is left.

Signs do not appear here. A deduction — an organisation fee charged against somebody’s reimbursement — is a transfer to the section, not a negative transfer from it.

source: Member | Section | Participants¶

Who owes the money.

destination: Member | Section | Participants¶

Who receives it.

amount: Decimal¶

How much, with at most two decimal places. The engine rejects anything finer: how to round is the section’s decision, and split() and pct() are there to make it.

category: str¶

What kind of money this is — "allowance", "ljp", whatever the ruleset wants to group and label by. Free text to the engine.

rule_id: str¶

Which rule produced it, for provenance: the stamp that answers „which statements paid a subsidy under which version of the rule“.

label: str¶

A short label for a person reading the payout, e.g. the bill’s own description.

explanation: str¶

Room for the arithmetic, if it is worth showing: „4 Tage × 22 €“.

class kompass.rules.Input(key: str, label: str, type: Literal['money', 'int', 'bool', 'text', 'choice', 'member', 'member_set'], required: bool = True, help: str = '', options: tuple[Member, ...] = (), max: int | None = None, choices: tuple[Choice, ...] = (), source: str = '', options_source: str = '', step: str = '', derived: bool = False)¶

One question the statement’s form has to ask.

Declaring the question beside the rule that reads the answer is what keeps the two from drifting apart: the form is generated from these, and a rule that reads an undeclared key fails loudly (see Inputs).

A declaration the engine cannot serve is refused where it is written, with RuleError: a choice with nothing to choose from, a source that names no context field, an options_source on a question that names no people. The engine refuses a nonsense Ruleset.balance for the same reason — it is a bug in the rules, and a case in the section’s own CI should fail on it rather than a person’s form quietly losing a question.

key: str¶

The key the answer is read back under.

label: str¶

What the person is asked, in the section’s language.

type: Literal['money', 'int', 'bool', 'text', 'choice', 'member', 'member_set']¶

Which widget to render (see InputType).

required: bool¶

Whether the statement may be handed in without an answer.

help: str¶

A sentence of help under the field.

options: tuple[Member, ...]¶

For member and member_set: who may be picked. The engine re-validates a submitted answer against this, so an answer can never name somebody the rule did not offer.

A ruleset either lists the people itself, out of the context it was given, or names an options_source and lets the engine fill this in. Not both.

max: int | None¶

For member_set and int: the largest acceptable count or value.

It bounds a submitted answer, which is refused on the way in, and an answer the engine supplies from a source, which cannot be — nobody can correct that one through the form. A supplied value that breaks this is therefore an error on the statement, naming the source and the bound, rather than a truncation: five youth leaders against three the section approved is something to fix on the excursion, and while there is an error nothing is persisted and no money moves.

choices: tuple[Choice, ...]¶

For choice: the alternatives, which a choice has to have. A submitted answer is re-validated against them, exactly as a person is re-validated against options.

source: str¶

Where the engine takes this answer from instead of asking for it: "excursion.kilometers" (see SOURCE_ROOTS).

When the source resolves, the engine supplies the value, the declaration comes back derived, and the form refuses a submitted answer for the key — the figure is corrected where it lives, not here. When it does not, this is an ordinary question whose answer is stored like any other. Either way a rule reads it the same way, which is the whole point: one ctx.inputs.number("kilometers") and no branch on where it came from.

A source resolves to nothing in exactly two cases: the root is absent (a statement with no excursion) or the field itself is None. A 0, an empty string and an empty set are values the statement records, so they are supplied like any other — a trip whose kilometres are still at the model’s default of 0 serves 0 and refuses a correction here, because the correction belongs on the trip. The nullable fields are StatementInfo’s two people and Excursion.ljp; every other field of Excursion always has a value.

Derivation is decided by Ruleset.inputs() and nothing else. A key Ruleset.relevant_inputs() names is served with the declaration inputs gave it, so the form and the rules cannot disagree about where one key’s value comes from.

It may not be stated beside options or options_source: a derived answer is not picked, so „these are the people who may be picked“ and „the value is whoever the trip says“ are two answers to one question. A derived set of people is bounded by max, and is statement-local already because the context is.

A derived value is not stored. It is resolved again every time a context is built, so there is no second copy to go stale when the trip changes.

options_source: str¶

Where the engine takes options from, for a member or member_set question: one of OPTION_SOURCES.

It is a request, and the engine’s answer is options. A declaration that comes back from the engine therefore carries one or the other and never both — which is also what a ruleset stating both is refused for.

step: str¶

The step this question belongs to, as a short label. Questions that share one are presented together, in the order the labels are first declared, and GET …/form serves that grouping. Empty is the unnamed step, which is what a form without steps is.

derived: bool¶

Whether the engine supplies this answer itself. The engine sets it; a ruleset declares source and reads this back, and setting it without a source is refused — it would be a question nobody can ever answer, refused with a message that is not true of it.

class kompass.rules.Constraint(name: str, description: str, applicable: bool, required: int, eligible: tuple[Member, ...], anyone_permitted: bool = False)¶

A signature the statement needs before the money moves.

Constraints are an unordered set: no priorities, no workflow. Each one asks for required signatures out of eligible, one signature counts against every constraint it satisfies, and applicable and satisfied are separate states — a constraint that does not apply is shown as such rather than hidden.

name: str¶

A short name, shown in the approval list.

description: str¶

Why this signature is needed, in the section’s words.

applicable: bool¶

Whether it applies to this statement at all.

required: int¶

How many signatures from eligible are needed.

eligible: tuple[Member, ...]¶

Who may sign. Re-checked against the real permission system, so naming somebody here cannot grant them a right they do not have.

anyone_permitted: bool¶

What it means for eligible to come out empty.

Left False, an empty group means nobody: the constraint stands open and no signature satisfies it. That is the safe reading, and it is the one an empty group usually deserves — a role nobody holds, a filter that matched nobody, a query that returned nothing — because the alternative lets a statement pay itself out precisely when the rules could not say who should allow it.

Set True, the engine fills the group from the holders of the section’s approval capability instead, which is what Kompass did before there were constraints at all. The forbids still apply to the group it fills in, so „whoever may act, except whoever is paid“ is sayable. An empty group then still means nobody — there is no reading under which „we could not work out who“ means „anyone will do“.

Somebody who may not sign, whatever permits them.

Forbids are subtracted from every constraint’s eligible set before quorum is counted, and they win unconditionally: this is how a conflict of interest is expressed („nobody who receives money from this statement“).

name: str¶

A short name, shown when a signature is refused.

applies_to: Callable[[Member], bool]¶

Whether this forbid catches a given candidate.

kompass.rules.split(amount: Decimal, n: int) → list[Decimal]¶

amount divided n ways, to the cent, adding back up exactly.

Each share is floored to the cent and the leftover cents are handed out one each from the top, in declaration order, so 99 cents five ways is 20, 20, 20, 20, 19 — every time, which is what makes a statement reproducible. Raises ValueError for n <= 0.

kompass.rules.pct(amount: Decimal, basis_points: int) → Decimal¶

basis_points ten-thousandths of amount, floored to the cent.

Basis points rather than a percentage because they are exact integers: pct(x, 9000) is 90 % of x, pct(x, 1990) is 19,9 %.

kompass.rules.quantize(amount: Decimal) → Decimal¶

amount floored to whole cents.

The rounding split() and pct() are built on: towards minus infinity, never away from zero, so repeatedly splitting an amount can never create money.
